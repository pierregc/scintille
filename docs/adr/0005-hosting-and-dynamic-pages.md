# 0005 · Cloudflare Workers with prerendered pages and on-demand storm and region pages

- Status: accepted
- Date: 2026-10-09

## Context
Storm pages (`/storms/<slug>`, #88) and region pages (`/live/<country>`, #90) appear and change
continuously, as the pipeline on the VPS detects storms and writes JSON to R2. A storm must get a
crawlable HTML page without a deploy (#88). Everything else (home, methodology, legal) changes only
with the code. The domain is already on Cloudflare, and the setup should stay cheap.

What current official sources say (see Sources):
- Cloudflare tells new projects to start on Workers. Workers serves static assets for free and
  without limit, and only runs the Worker script for requests that do not match a file.
- Workers Free: 100,000 requests per day per account (reset at 00:00 UTC), 10 ms CPU per request,
  hard errors past the limit. Workers Paid: from 5 USD/month with 10 million requests and 30 million
  CPU ms included, then billed per use.
- Pages Free: 500 Git builds per month. An hourly rebuild alone would need 720 to 744.
- `@astrojs/cloudflare` (v13+, required since Astro 6) only targets Workers. Pages stay prerendered
  by default; `export const prerender = false` renders one route on demand. Bindings, including R2,
  are imported from `cloudflare:workers`.
- The Workers Cache API (`caches.default`) is per data center and does not support
  `stale-while-revalidate` or `stale-if-error`. Every request it serves still runs the Worker.
- Version preview URLs reuse the version's configured resources. Cloudflare points to Previews for
  isolated branch testing; Previews do not duplicate R2, a separate bucket must be bound.

## Options
- **Astro static + on-demand routes on Workers, reading R2 through a binding.** A page exists as
  soon as its JSON is in R2, no build quota is involved, and crawlers get plain HTML. Costs: a
  runtime on the request path, the Free caps on dynamic routes, and caching to design.
- **Same, on Pages Functions.** The current Astro adapter no longer supports Pages. Rejected.
- **Astro SSR on the existing Hetzner VPS (Node adapter), behind Cloudflare.** Same engine, no
  10 ms CPU limit. Rejected: the site's availability would depend on the machine that runs the
  pipeline, and we would operate a web server for a few dynamic routes.
- **Fully static, rebuilt a few times a day by GitHub Actions.** Simplest at request time, but new
  storms wait hours for a page (fails #88), and every rebuild regenerates the whole archive.
- **Country pages prerendered, live stats loaded in the browser.** The set of countries is known,
  but crawlers would not see the stats in the HTML, which is the point of these pages. Rejected.
- **Pages generated by the pipeline.** Already rejected in ADR 0002 (a second rendering stack).

## Decision
Deploy `web/` as one Cloudflare Worker with static assets through `@astrojs/cloudflare`. Every page
is prerendered except `/storms/[slug]`, `/storms` (paginated index) and `/live/[country]`, which
render on demand from JSON read through an R2 binding. Sitemaps for those pages are prepared by the
pipeline. Deploys go through GitHub Actions with Wrangler. Start on Workers Free; confirm or switch
to Paid on measurements before the public launch.

## Consequences
- **Data contract.** The pipeline publishes, with a `schema_version`, `published_at` and last
  observation time on each file:
  - `storms/<slug>.json` and `regions/<country>.json`, each with a maximum size;
  - `storms/index/<page>.json`, fixed-size pages prepared by the pipeline, so a request never parses
    the whole archive;
  - `sitemaps/*.xml`, at most 50,000 URLs and 50 MiB per file, plus their index.

  Publication order: detail files first, then index pages, then sitemaps, so an index never points
  to a missing file.
- **Response rules for dynamic pages.**

  | Situation | Response |
  |---|---|
  | Unknown slug, or country never covered by any source | 404 |
  | Covered country, no recent detection | 200, explicit and timestamped "no lightning detected" |
  | Partially covered country | 200, coverage limits shown |
  | Data older than expected | 200, last data with a staleness warning |
  | R2 unreachable | 503 |

  Countries outside all satellite coverage get no page: it would say nothing but "no data", and
  the coverage gap is already explained on the methodology page.
- **Caching.** Rendered pages are stored with `caches.default` and a plain TTL: about 5 minutes
  while a storm is active, 1 day once it is closed, 60 seconds for a 404. No `stale-while-revalidate`
  (not supported). The cache key includes the deployed version, so a deploy never serves HTML from
  an old template. Browser `max-age` stays short (60 s) and separate from the edge TTL, because a
  purge cannot reach browsers. This cache saves rendering and R2 reads, not Worker requests.
- **Invalidation.** Short TTLs make purges an optimization, not a requirement. When the pipeline
  updates a closed storm, it purges in one batched call the tags that page feeds: `storm:<slug>`,
  each affected `region:<cc>`, and `storms-index`. A failed purge is retried and is harmless
  anyway: the TTL bounds staleness. Purge limits on Free: 5 tag/prefix/host requests per minute,
  up to 100 items per request.
- **Free plan as a measured hypothesis.** Static assets are served before the Worker runs, so only
  dynamic routes count toward 100,000 requests a day (about 1.2 per second on average, bots
  included). `run_worker_first` stays off. Before the public launch, measure with a cold cache:
  p99 CPU of a storm page, of the largest index page and of a rich region page. If p99 is close to
  10 ms or traffic projections are close to the daily cap, move to Workers Paid. No code change is
  needed. We do not add complexity just to stay on Free.
- **Workers Cache and Astro's `cacheCloudflare()` stay off**: with Workers Cache on, every static
  asset request is billed as a Worker request. Revisit on Workers Paid or once the provider is
  stable (it requires adapter 14+).
- **Deployment (#16).** Production deploys on push to `main` after checks pass (`wrangler deploy`).
  Each PR gets a Preview bound to a separate `scintille-live-preview` bucket, seeded from the
  repository fixtures, so a PR can never write to production data. Previews send
  `X-Robots-Tag: noindex`. `scintille.app` is attached as a Worker custom domain.
- **Terraform (#18).** Terraform owns DNS (apex and a proxied `www` record, needed for the
  redirect), the three R2 buckets, CORS, the `www` → apex redirect rule and zone settings (Always
  Use HTTPS, HSTS). CORS allows `https://scintille.app` and only our own preview subdomain
  (`https://*.<our-subdomain>.workers.dev`), never all of `workers.dev`. Wrangler owns the Worker,
  its versions, its custom domain and its bindings.
- **Tokens (#17).** The deploy token needs Workers Scripts Write (also required to attach a custom
  domain) and Workers R2 Storage read on the buckets it binds; the exact scopes are confirmed in #16
  from the API calls Wrangler actually makes. The pipeline gets a separate token limited to cache
  purge on the zone.
- **Dev.** `astro dev` runs on `workerd` with the adapter; local storm pages read a local R2
  binding seeded with the same fixtures as previews.
